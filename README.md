# Kharcha

Android-first, offline-first personal expense tracker. All data lives in a
local SQLite database on the device — no backend, no authentication, no cloud
sync, and no external API calls are involved in any core functionality.

## Stack

| Concern        | Choice                                               |
| -------------- | ---------------------------------------------------- |
| Framework      | Expo (SDK 57) with committed `android/` via prebuild |
| Language       | TypeScript (strict)                                  |
| UI             | React Native 0.86 (New Architecture, Hermes)         |
| Navigation     | React Navigation 7 (native stack + bottom tabs)      |
| Local database | op-sqlite (JSI-bound SQLite)                         |
| App state      | Zustand (settings such as theme mode, currency)      |
| Icons          | @expo/vector-icons (Ionicons)                        |
| Quality        | ESLint (expo flat config), Prettier, Jest            |

## Architecture

Feature-based structure. Shared building blocks live at the top level of
`src/`, features are self-contained under `src/features/`:

```
kharcha/
├── app.json                  # Expo config (android package: com.kharcha)
├── index.ts                  # Entry point -> src/App
├── android/                  # Generated by `expo prebuild`, committed
└── src/
    ├── App.tsx               # DB bootstrap gate + providers
    ├── components/ui/        # Reusable primitives (Screen, Text, Button,
    │                         # TextInput, Card, EmptyState, Fab)
    ├── database/             # Schema, migrations, repositories, service (see below)
    ├── features/
    │   ├── add-expense/      # Modal opened from the central FAB
    │   ├── home/             # Dashboard (placeholder)
    │   ├── more/             # Settings hub incl. working theme toggle
    │   ├── reports/          # Insights (placeholder)
    │   └── transactions/     # Expense list (placeholder)
    │       └── screens/      # Each feature grows: components/, hooks/,
    │                         # services/, types.ts as needed
    ├── navigation/           # Root stack, tab bar with central FAB, types
    ├── store/                # Zustand stores (settingsStore)
    ├── theme/                # Design tokens (light+dark) + ThemeProvider
    └── utils/                # formatCurrency etc. (unit tested)
```

### Navigation model

Four tabs — **Home, Transactions, Reports, More** — with the primary
**Add Expense** action as a prominent floating button centered in the tab
bar (deliberately not a fifth tab). The FAB opens the `AddExpense` screen
as a modal from the root stack.

### Theme system

`src/theme` defines color, spacing, radius and typography tokens. Light and
dark palettes share one shape; `ThemeProvider` swaps them based on
`themeMode` in the Zustand settings store, and the toggle lives in the More
tab. Components never hardcode colors — they read `useTheme()`.

### Database layer

Fully implemented, engine-agnostic, and tested against a real SQLite engine.

```
src/database/
├── driver.ts               # DatabaseDriver interface (exec/query/run) — the only
│                           #   abstraction any repository talks to
├── drivers/
│   ├── opsqlite.ts         # Production driver (op-sqlite, JSI, kharcha.db)
│   └── node.ts             # TEST-ONLY driver (Node built-in node:sqlite);
│                           #   never imported by app code, never bundled by Metro
├── migrations.ts           # Versioned runner (PRAGMA user_version) + registry
├── models.ts               # Type-safe entities, drafts, patches, filters, enums
├── errors.ts               # DatabaseError / MigrationError / ValidationError / NotFoundError
├── transaction.ts          # withTransaction helper (BEGIN IMMEDIATE ... COMMIT/ROLLBACK)
├── repositories/           # One CRUD repository per table + input guards
│   ├── expenses.ts         # create/get/list/filter/count/sum/update/delete
│   ├── income.ts           # same shape as expenses
│   ├── categories.ts       # + findByName, isNameTaken, countByType
│   ├── budgets.ts          # + upsert (one budget per category/month), listByMonth join
│   └── settings.ts         # get/set/setMany/getAll (string values, JSON if needed)
├── service.ts              # DatabaseService facade: open → migrate → ready
├── connection.ts           # App-wide singleton (memoized openDatabase())
└── testing/helpers.ts      # Test fixtures (never bundled)
```

**Schema (migration 001 — `initial_schema`):**

| Table        | Notes                                                                                                                                                                                                           |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `categories` | `type` CHECK `('expense','income')`; UNIQUE `(name, type)`; `is_default` 0/1; 16 seeded defaults (10 expense, 6 income)                                                                                         |
| `expenses`   | `amount` minor units CHECK `> 0`; FK → `categories` **ON DELETE RESTRICT**; CHECK-constrained `payment_method` (`cash`, `card`, `bank_transfer`, `mobile_wallet`, `other`); indexes on `date` and `category_id` |
| `income`     | FK-free by design — `source` is free text; seeded income categories act as UI presets; index on `date`                                                                                                          |
| `budgets`    | One budget per `(category_id, year, month)` (unique index); FK → `categories` **ON DELETE CASCADE**; CHECKs on `amount`, `month` (1-12), `year` (2000-2100)                                                     |
| `settings`   | `key` TEXT PRIMARY KEY, `value` TEXT (serialize structured values as JSON)                                                                                                                                      |

An expense/budget `categoryId` must reference a category of the matching
type — a rule SQLite cannot express, so repositories enforce it in code
(`assertCategoryOfType`) and it is covered by tests.

**Testing approach:** every test runs the REAL migration runner and
repositories against a real SQLite engine via Node's built-in `node:sqlite`,
through the same `DatabaseDriver` interface used in production. Jest docblock
`@jest-environment node` opts the suites out of jest-expo's default
environment. Run with `npm test`.

**Money rule:** amounts are stored as integers in minor units (e.g. paisa)
and converted to display strings only at the UI edge via
`utils/format.ts`. This avoids floating-point drift in sums and reports.

**Dates rule:** `date`, `created_at`, `updated_at` are epoch milliseconds.

### Adding a new migration

Published migrations are immutable. Append to the registry in
`src/database/migrations.ts` with the next version number:

```ts
const MIGRATION_002_EXAMPLE: Migration = {
  version: 2,
  name: 'example_change',
  statements: [`ALTER TABLE ...`],
};

export const MIGRATIONS: readonly Migration[] = [
  MIGRATION_001_INITIAL_SCHEMA,
  MIGRATION_002_EXAMPLE,
];
```

### Adding a feature

1. Create `src/features/<name>/` with a `screens/` (and later `components/`,
   `hooks/`, `services/`, `types.ts`) as the feature grows.
2. Register the screen in `src/navigation/` and add route types in
   `navigation/types.ts`.
3. Feature-local state stays in the feature; only true app-wide state goes
   into `src/store/`.

## Building for Android locally

Requirements: Node 18+, JDK 17+, Android Studio (SDK 35, build-tools, platform
tools). This sandbox has no Android SDK, so the native build was validated
structurally (prebuild + autolinking config) and the JS graph via
`expo export`; run the actual compile on a machine with Android tooling:

```bash
npm install
npm run android:build     # debug build onto device/emulator
# or
cd android && ./gradlew assembleDebug   # plain Gradle, APK in android/app/build/outputs
```

First Gradle run downloads dependencies and can take several minutes.

## Intentionally NOT implemented yet

Per the project brief, the database layer is complete and tested, but the
features on top of it are deferred and have placeholders/TODOs in place:
expense/income creation flows and persistence wiring, the transactions list,
reports/charts, category management UI, data export, settings persistence
(`settingsStore` still resets on restart — the `settings` table + repository
are ready for it), and any custom fonts.
